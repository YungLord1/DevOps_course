# Роль CRI-o

## Подробное описание
Эта роль отвечает за установку **CRI-O** — легковесного рантайма для запуска контейнеров в Kubernetes. Подгружает нужные сетевые модули ядра, настраивает маршрутизацию (sysctl), прокидывает ключи и конфигурации. 

Роль адаптирована для работы в изолированных средах (через прокси) и поддерживает тестирование через Molecule.

---

## Логика
При запуске роль выполняет следующие шаги:
1. **Подготовка директорий:** Создает системные папки `/etc/crio/crio.conf.d`, `/etc/modules-load.d` и `/etc/apt/keyrings` с нужными правами доступа.
2. **Настройка ядра (Modprobe):** Прописывает в `/etc/modules-load.d/crio.conf` и сразу активирует модули:
   * `overlay` — для работы слоистой файловой системы контейнеров.
   * `br_netfilter` — для корректной работы сетевых плагинов (CNI) и iptables.
3. **Настройка сети (Sysctl):** Применяет правила в `/etc/sysctl.d/k8s.conf`:
   * Включает `ip_forward` (маршрутизация транзитного трафика).
   * Заставляет iptables видеть бридж-трафик (`bridge-nf-call-iptables`).
   * Отключает использование файла подкачки (`vm.swappiness = 0`), что критично для стабильности Kubelet.
4. **Репозитории и пакеты:** Скачивает GPG-ключ Kubernetes, добавляет репозиторий для версии 1.32, скачивает локальный `.deb` файл CRI-O (чтобы избежать таймаутов) и устанавливает его.
5. **Конфигурация:** Создает Jinja-шаблон `99-defaults.conf.j2` в настройки CRI-O, указывая драйвер хранилища, `systemd` как cgroup-менеджер и пути к CNI.
6. **Запуск:** Активирует и запускает службу `crio.service`.

---

## Используемые зависимости
Для работы конфигурации ядра используются модули из внешних коллекций:
* **`ansible.posix`** (модуль `sysctl`)
* **`community.general`** (модули `ini_file` и `modprobe`)

---

## Переменные роли

Все значения по умолчанию хранятся в `defaults/main.yml`.

| Переменная | Тип | По умолчанию | Описание |
|---|---|---|---|
| `cri_o_version` | String | `"1.32"` | Целевая версия рантайма CRI-O. |
| `cri_o_crio_root` | Path | `"/tmp/crio"` | Путь для постоянного хранения данных контейнеров (images). |
| `cri_o_crio_runroot` | Path | `"/run/containers/storage"` | Путь для временных (runtime) данных контейнеров. |
| `cri_o_crio_storage_driver` | String | `"overlay"` | Основной драйвер ФС. *Примечание: в Molecule автоматически меняется на `vfs`.* |
| `cri_o_runtime_endpoint` | URL | `"unix:///var/run/crio/crio.sock"` | Путь к UNIX-сокету, через который Kubelet будет общаться с CRI-O. |
| `cri_o_modprobe` | List (Dict) | `[{br_netfilter}, {overlay}]` | Список модулей ядра для загрузки. |
| `cri_o_sysctl` | List (Dict) | `[ip_forward, swappiness...]` | Настройки ядра (sysctl) для сети K8s. |

---

## Handlers (Обработчики)
* **`cri_o | restart modules`** — перезапускает `systemd-modules-load`, если обновился конфиг в `modules-load.d`.
* **`cri_o | restart service`** — дергает рестарт службы `crio`, если изменился файл конфигурации `99-defaults.conf`.

## Тестирование (Molecule)

**Особенности тестов:**
Так как Docker контейнеры плохо переваривают драйвер `overlay` внутри себя (возникает конфликт "вложенных" ФС), в `molecule/default/converge.yml` реализована умная подмена:
```yaml
storage_driver = "{{ 'vfs' if ansible_virtualization_type == 'docker' else cri_o_crio_storage_driver }}"

### Проверки Testinfra (`test_default.py`)

Для корректности установки роли используются автоматические тесты на Python. Основные проверки включают:

* Контроль прав доступа: * Проверка файла /etc/hosts: он должен существовать, а владельцем должны быть root:root.
* Состояние пакетов:
    * Убеждаемся, что пакет cri-o действительно установлен в системе через менеджер пакетов.
* Статус сервиса (Systemd):
    * Проверка службы crio: она должна быть не просто запущена (`running`), но и добавлена в автозагрузку (`enabled`), чтобы рантайм поднялся после ребута ноды.
* Проверка сокета (Runtime Check):
    * Физическое наличие UNIX-сокета /var/run/crio/crio.sock. Это критически важная проверка, так как именно через этот файл kubelet общается с контейнерами. Если сокета нет — кластер не заведется.

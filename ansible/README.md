# Иправленное домашнее задание №5 по Ansible

## Краткое описание
В проекте настраиваются сервера (мастер и воркеры), устанавливается контейнерный рантайм `cri-o` и базовые утилиты кластера (`kubelet`, `kubeadm`, `kubectl`). Все чувствительные данные (например, прокси с логинами и паролями) спрятаны в Ansible Vault. Тестирование ролей настроено через Molecule (Testinfra).

## Используемые зависимости
Все зависимости лежат в файле `collections/requirements.yml` и устанавливаются в локальную папку.
* `ansible.posix` (версия 1.4.0) — для работы с ядром (sysctl).
* `community.general` (версия 10.7.6) — для работы с модулями ядра (modprobe) и ini-файлами.
* `ansible.scm`, `ansible.utils`, `cisco.ios`, `network.backup` (дополнительные утилиты).

## Переменные проекта (Vault)
Глобальные переменные заданы через Ansible Vault в файле `vars_vault/vault_proxy.yml`.

| Переменная | Тип | Значение по умолчанию | Описание |
|---|---|---|---|
| `my_proxy.http_proxy` | String (Vault) | - | Зашифрованная строка с HTTP-прокси (с логином/паролем) |
| `my_proxy.https_proxy` | String (Vault) | - | Зашифрованная строка с HTTPS-прокси |
| `my_proxy.no_proxy` | String | `"localhost, 127.0.0.1,10.184.0.0/24"` | Исключения для проксирования |

## Playbook
Запуск осуществляется через `playbook.yml`. 

```yaml
---
- name: Push cri-o and kubelet on all servers
  hosts: myVMs
  vars_files:
    - ./collections/ansible_collections/demo/demo/vars_vault/vault_proxy.yml
  become: true
  environment:
    http_proxy: "{{ my_proxy.http_proxy }}"
    https_proxy: "{{ my_proxy.https_proxy }}"
  roles:
    - role: cri_o
      tags: crio
    - role: kube
      tags: k8s

```
Команда для запуска:
ansible-playbook playbook.yml -K (Флаг для ручного ввода пароля)


#Ошибки, с которыми я столкнулся, и как их решил
Во время исправления  я наткнулся на следующие моменты:

1. Прокси
APT наотрез отказывался нормально обновлять кэш и качать пакеты (выдавал Connection Refused и таймауты). Модули Ansible с environment иногда игнорировали прокси.

Решение: Создавал костыль — временный файл /etc/apt/apt.conf.d/99proxy с хардкодом прокси (Acquire::http::Proxy...), а также прокидывал прокси через переменные окружения напрямую в тасках. По итогу сначала одно, а потом второе прокси попали похоже в  рейт лимит или заблокировались на время.

2. Боль с Jinja, Molecule и хранилищем CRI-O
При тестах в Molecule (через Docker) контейнеры падали из-за конфликта драйверов хранилища (overlayFS внутри Docker вел себя неадекватно). Ошибка данных внутри контейнера возвращалась снова и снова.

#Решение:
1. Решил конфликты драйвера: сменил storage_driver на vfs, так как он, как я понял, почти не конфликтует внутри Docker. Добавил логику в плейбук молекулы: vfs, если мы в докере, и overlay, если на реальном сервере.
2. Изменил приоритет конфига Jinja шаблона 99-defaults.conf.j2. Самое высокое число будет переопределяться последним.
3. Поправил пути к шаблонам через дефолтные переменные. Изначально я ошибся с путями и запихиванием даты в контейнер (данные качались не туда, куда нужно).

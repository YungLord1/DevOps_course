# CI/CD Pipeline в Kubernetes

## Описание проекта
В рамках данной работы был реализован полный цикл автоматизации (CI/CD) для моего  API приложения. Приложение упаковано в Docker, разворачивается в кластере Kubernetes с помощью Helm и проходит автоматические проверки безопасности и работоспособности.

---

## Стек
* **Инфраструктура:** Kubernetes (K8s), MetalLB (LoadBalancer), Traefik (Ingress Controller).
* **CI/CD:** Jenkins, Shared Libraries, Pipeline.
* **Инструменты:** Helm 4, Docker (Podman), Kubectl.
* **Тестирование:** Pytest (Smoke), DAST (Security Scan).

---

## Архитектура пайплайна

Пайплайн разделен на логические этапы, чтобы гарантировать надежность деплоя:

1.  **Сборка и Пуш:** Jenkins собирает Docker-образ и отправляет его на Docker Hub.
2.  **Подготовка окружения:** Автоматическое создание Namespace и `imagePullSecrets` (секреты для скачивания образа).
3.  **Helm Deploy:** Деплой чарта с динамической подстановкой TLS-сертификатов.
4.  **Сетевой туннель:** Использование `kubectl port-forward` для доступа к приложению внутри кластера из Jenkins-воркера.
5.  **Smoke tests + DAST:** Параллельный запуск функциональных тестов и сканера безопасности.
6.  **Manual Approval:** Ручное подтверждение для выкатки в Production.

---

## Структура Helm-чарта
Особенность этого чарта в том, что он включает в себя не только само приложение, но и конфигурацию всей необходимой инфраструктуры.

| Файл | Описание |
| :--- | :--- |
| **`deployment.yaml`** | Описание подов приложения, лимитов и прав доступа к реестру (`regcred`). |
| **`service.yaml`** | Внутренний сервис для связи подов приложения внутри кластера. |
| **`ingress.yaml`** | Правила маршрутизации трафика и привязка TLS-сертификатов. |
| **`secret-tls.yaml`** | Создание секрета с сертификатами для работы HTTPS. |
| **`metallb-config.yaml`** | Настройка пула IP-адресов для балансировщика MetalLB. |
| **`traefik-*.yaml`** | Набор файлов (Deployment, RBAC, Service) для развертывания Ingress-контроллера Traefik. |
| **`values.yaml`** | Главный файл с переменными, где настраивается всё — от портов до тегов образов. |

---

## Управление инфраструктурой (Traefik и MetalLB)
В файле `values.yaml` предусмотрены логические переключатели (флаги), которые позволяют управлять составом деплоя:

* **Установка "с нуля":** Если в кластере еще нет контроллера трафика или балансировщика, мы выставляем соответствующие флаги в `true`. Тогда Helm сам развернет всю инфраструктуру вместе с приложением.
* **Использование готовой среды:** Если Traefik и MetalLB уже установлены в кластере (например, админом), мы просто меняем значение на `false`. В этом случае Helm деплоит только наше приложение, не создавая лишних сущностей и не вызывая конфликтов.

**Почему это удобно:**
Это избавляет от необходимости запускать десятки команд `kubectl apply`. Весь стек — от выдачи IP-адреса до запуска кода — управляется одной командой `helm upgrade --install`. Это делает процесс деплоя предсказуемым и воспроизводимым на любом чистом кластере.

---

## Параметры сборки
При запуске пайплайна в Jenkins доступны следующие настройки:

* **IMAGE_TAG**: Версия образа (автоматически подтягивается из реестра).
* **ENVIRONMENT**: Выбор окружения (`staging` / `production`).

---

## Почему выбраны такие решения?

* **Почему Helm?** Это стандарт индустрии. Он позволяет делать `helm rollback` в случае неудачных тестов и хранит историю всех изменений в кластере.
* **Почему не ArgoCD?** Для учебного проекта и одного микросервиса ArgoCD — это избыточно (слишком много ресурсов кластера на поддержку самой системы). Jenkins + Helm позволяют реализовать "Push-модель", которая проще в отладке и прозрачнее для понимания процессов.
* **Port-Forwarding:** Это решение позволило запускать тесты на закрытом внутреннем контуре, не выставляя приложение в интернет до того, как оно пройдет проверки безопасности.
